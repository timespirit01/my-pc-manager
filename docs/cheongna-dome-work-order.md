## A. 고척스카이돔 작업 정리

### A-1. 결과물

| 항목 | 내용 |
|---|---|
| 공개 주소 | https://gocheok-dome-3d.vercel.app/ (예: `#seat=405/1/3`, `#seat=R.d/3/18`) |
| 코드 | `gocheok-dome-3d/` (브랜치 `claude/gocheok-dome-3d-baseball-t4bhw1`) |
| 형태 | 빌드 없는 정적 웹앱 (three.js 0.170 을 `vendor/`에 포함) |
| 좌석 | 모델 16,259석 (공식 16,744석), 구역 128곳 |
| 좌석 시야 | 사진급 360° 파노라마 286장 (Blender Cycles), 3D 모델로 전환 가능 |
| 배포 | Vercel 프로젝트 `gocheok-dome-3d` (팀 `team_tRGcbGSm9Kml30p2XAHyLdQo`), Git 연동 배포 |

**주요 기능**
- 전체 → 구역 → 좌석 → 1인칭 시야로 이동합니다.
- 좌석 배치도 창(층별), 미니맵, 옆 구역·옆자리·앞뒤 열 이동을 지원합니다.
- 시야 링크 공유(`#seat=구역/열/번호`), 야구·콘서트 모드, 등급·요금 표시, 모바일 UI가 있습니다.
- 좌석 시야는 3D로 날아간 뒤 360° 사진으로 바뀝니다. 고른 좌석과 가장 가까운 렌더 지점의 사진을 씁니다.
- 배지를 누르면 3D 모델로 전환되고, 콘서트 모드에서는 3D로 보입니다.

### A-2. 진행 순서 (커밋 기준)

1. 공개 제원·좌석 구역 조사 → 절차적 3D 모델 + 좌석 시야 웹앱
2. 코드 리뷰·접근성 점검, 모바일 UI 수정
3. 공개 가상투어(Cupix)와 대조해 형상 보정
4. MLB 레드삭스(Fenway, 3D Digital Venue) 좌석맵을 참고한 사용성 개선 7가지
   - 배치도 창, 경로 표시, 옆 구역 이동, 미니맵, 공유 링크 등
5. Blender로 에셋 품질 향상: 좌석 hi/lo, 스탠드 AO, 지붕 트러스
6. Cycles 조명 굽기
   - 그라운드·스탠드 라이트맵, 정점 색, 좌석별 밝기
   - 큐브 반사로 광택 표현
7. 가상투어 3개 지점에서 카메라를 역산해 형상 재보정 → 조명 재굽기
8. Gemini 비교 검수 스크립트: 사진 vs 같은 시점 렌더 → 차이점 JSON
9. 렌더 전용 고디테일 + 360° 파노라마 파이프라인(`render_pano.py`)
10. 앱에 360° 뷰어(`src/pano.js`) 추가
11. GPU(L40S)로 286장 렌더 → WebP 변환 → 배포

### A-3. 파이프라인 (재사용 대상)

```
src/data.js (제원·층 단면·구역)
  └ src/stadium.js  절차적 형상 (웹)
      ├ tools/export_scene.cjs → tools/blender/build_assets.py → assets/*.glb (스탠드·좌석·트러스)
      ├ tools/blender/bake_lighting.py → assets/bake/* (라이트맵·정점색·좌석 밝기)
      └ tools/export_bake.cjs → bake_scene.glb, bake.json(anchors), panos.json(렌더 지점)
            └ tools/blender/render_pano.py
                 views : 가상투어와 같은 시점 렌더 (CPU, 비교용)
                 pano  : 360° 등장방형 4096×2048 (GPU)
            └ tools/ai/gemini_review.py  사진 vs 렌더 차이 JSON
            └ tools/pano_pack.py → assets/panos/{4k,2k}/*.webp + index.json
src/pano.js  360° 뷰어 (3D 카메라 시선을 그대로 따름)
```

**좌표 규칙**
- three.js: y-up, 홈플레이트 = 원점, 중견 방향 = −z.
- Blender: `tb(x,y,z) = (x, −z, y)`.
- 구역 각도 φ: 0° = 중견, 90° = 1루, 180° = 포수 뒤.

**360° 방향 규칙**
- Blender 카메라 `rotation_euler = (π/2, 0, atan2(−dx, dy))` → 이미지 가운데가 마운드 방향이 됩니다.
- 웹: 구(`scale(-1,1,1)`)를 `rotation.y = atan2(dz, −dx)` 로 돌립니다. d = 마운드 − 눈 위치(three 좌표).

### A-4. 렌더 전용 디테일 (웹에는 없음)

- 개별 좌석: 기하 노드 인스턴스, 구역 색 × 정점 색.
- 난간: 유리·철제 난간(세로 살 12cm), 계단 반단 + 노란 디딤판.
- 그물: 절차적 격자, 선이 화소보다 가늘어 흐리게 보이도록 투명도 조정.
- 지붕·벽: 흰 격자 둘레 벽, 촘촘한 흰 입체 지붕 트러스(144×10).
- 기타: 조명 기구, 외야 펜스 노란 띠.
- 색 보정: 잔디·트랙 채도, 막 색, 노출.
- 카메라가 앉은 의자는 숨깁니다.

### A-6. 시행착오와 교훈 (청라돔에서 반드시 피할 것)

1. **Gemini 검수는 틀린 지적도 섞여 있습니다.** 실제로 있는 폴·더그아웃을 "없다"고 했습니다. 지적마다 광선 검사나 겹쳐 보기로 확인한 뒤에만 고칩니다.
2. **원인 모를 물체는 광선 검사(`scene.ray_cast`)로 찾습니다.** 이번에 이렇게 찾은 것들입니다.
   - 홈 뒤 검은 링 = 그물 상단 레일
   - 정중앙 기둥 = 웹에서만 숨긴 그물 기둥
   - 검은 덩어리 = 어두운 스탠드 재질
3. **모든 객체에 이름을 붙이고 이름 목록을 함께 내보냅니다.** 웹에서만 숨기는 객체(그물, 기둥, 굵은 케이블)는 렌더에서도 이름으로 숨깁니다.
4. **층과 층이 만나는 곳의 벽을 꼭 검사합니다.**
   - 문제: 1층 맨 뒤 벽(2.6m)이 2층 바닥보다 1.6~1.8m 높아 2층 시야를 가렸습니다. 2층 파노라마 24장을 다시 렌더했습니다.
   - 대책: 렌더 전에 모든 렌더 지점에서 홈·마운드·폴 방향으로 광선을 쏴 그라운드 전에 막히는지 자동으로 검사합니다(B-5 참고).
5. **좌석 대표 지점이 하나면 앞열·뒷열 시야가 크게 다릅니다.** 6열 이상 구역은 앞·가운데·뒤 3지점을 렌더합니다.
6. **모바일 세로 화면은 좌우 화각이 좁습니다.** 기본 세로 시야각을 78°로 넓혔습니다.
7. **네트워크**: 이 환경(`timespirit`)에 허용 호스트 `upload.higgsfield.ai`와 `d2ol7oe51mr4n9.cloudfront.net`을 추가했습니다(GPU 파일 주고받기). Gemini 키는 `generativelanguage.googleapis.com` 네트워크 비밀값으로 저장돼 있습니다. 같은 환경으로 새 세션을 열면 그대로 쓸 수 있습니다.
8. **GPU 작업 흐름**
   - 파일 보내기: `media_upload`(zip·json·py) → curl PUT(`Content-Type: application/octet-stream`) → `media_confirm` → 서버에서 CDN URL을 curl로 받기.
   - `gpu_rental_exec`는 1회 최대 90초입니다. 긴 작업은 `nohup` + 로그 확인으로 돌리고, 여러 단계는 "앞 단계 완료 표시를 기다리는 체인 스크립트"로 잇습니다.
   - 끝나면 바로 `gpu_rental_stop`. `/workspace`는 남습니다(고척 파일이 `/workspace/gocheok`에 있음).
9. **Blender**
   - 설치: `uv`로 Python 3.13 + `pip install bpy==5.3.0`. OptiX 커널이 휠에 들어 있습니다.
   - GPU 선택: L40S 또는 RTX PRO 6000. H100/H200/B200은 RT 코어가 없어 피합니다.
10. **Vercel**
    - Git 연동 배포: `create_deployment` + `gitSource.sha`, 루트 폴더 지정.
    - 미리보기는 SSO 보호이고, 공개 주소 반영은 사용자 승인 후 `target: production`.
    - 148MB 정적 자산도 문제없이 배포됐습니다.
11. **Higgsfield 크레딧**: 같은 계정의 다른 앱(Seedance 영상 등)이 크레딧을 크게 쓴 기록이 있습니다. GPU를 빌리기 직전에 잔액을 확인합니다(2026-11-24 기준 **161.66 크레딧**).

## B. 청라돔 작업지시서

### B-1. 목표

인천 청라 돔구장(SSG 랜더스 신구장, 건설 중)의 **좌석 시야 3D 웹서비스**를 고척돔과 같은 수준 이상으로 만듭니다.

- **품질 기준**: 고척돔 결과물 이상. 최소한 Fenway 좌석맵(3D Digital Venue) 수준입니다.
- **핵심**: 경기장 형상 정확도와 좌석별 시야각. 사람(관중·선수)은 무거우면 뺍니다.
- **출발점**: 사용자가 만든 **간단한 Blender 모델**입니다. 이를 **조감도·투시도에 맞춰 고품질화**합니다.

### B-2. 고척돔과 다른 점 (설계 원칙)

| 항목 | 고척돔 | 청라돔 |
|---|---|---|
| 실물 | 있음 (가상투어 사진으로 보정) | **미완공** → 실사 사진 없음 |
| 기준 자료 | 공개 제원 + 가상투어 3지점 | **조감도·투시도·공식 발표 제원·좌석 배치도** |
| 형상 원천 | three.js 절차 모델 → Blender | **Blender 모델이 원천** → glTF로 웹에 내보냄 |
| 보정 방법 | 사진 속 기준점으로 카메라 역산 | 조감도 속 기준점(홈·베이스·폴·지붕 높이)으로 카메라 역산 |

- 사실 확인 필요 항목: 좌석 수, 펜스 거리, 지붕 높이·형식, 층 구성, 구역 번호. 웹에서 조사하고 **출처를 `data` 파일 주석과 README에 남깁니다.** 추정값은 "추정"이라고 표시합니다.
- 조감도는 설계 단계 이미지라 최종 시공과 다를 수 있습니다. 앱 안내문에 "설계 자료 기준 예상 시야" 문구를 넣습니다.

### B-3. 사용자가 준비할 것

1. **Blender 파일**(`.blend`)과 만든 Blender 버전. 저장소 `cheongna-dome-3d/reference/model/`에 올리거나 채팅에 첨부합니다. 100MB가 넘으면 미리 알려 주세요.
2. **조감도·투시도 이미지** (여러 각도, 가능한 큰 해상도) → `cheongna-dome-3d/reference/images/`
3. 있으면: 좌석 배치도(구역 번호), 단면도·평면도, 공식 발표 제원(보도자료 링크)
4. 예산 승인: GPU 크레딧 상한, Gemini API 사용

### B-4. 저장소 구성 (권장)

같은 저장소에 새 폴더를 만들어 고척돔 코드를 재사용합니다.

```
cheongna-dome-3d/
  index.html, src/ (gocheok-dome-3d 에서 복사 후 수정)
  src/data.js        청라돔 제원·구역·등급 (출처 주석)
  assets/            Blender 에서 내보낸 glb, 구운 조명, panos/
  reference/         사용자 제공 모델·조감도 (원본은 수정 금지)
  tools/blender/     모델 정리·좌석 생성·조명 굽기·360° 렌더 스크립트
  tools/ai/          gemini_review.py (그대로 재사용)
```

- 브랜치는 새로 만듭니다(예: `claude/cheongna-dome-3d`). Vercel은 새 프로젝트(`rootDirectory: cheongna-dome-3d`)로 만듭니다.
- 고척돔 폴더·배포는 건드리지 않습니다.

### B-5. 단계별 작업

각 단계 끝에 **사용자 확인 지점(★)**이 있습니다. 비용이 드는 작업과 공개 배포는 반드시 승인을 받은 뒤 진행합니다.

**0단계 — 준비와 점검**
- 자료를 조사해 제원표를 만듭니다. 항목마다 출처와 신뢰도를 적습니다.
- 사용자 Blender 모델을 점검해 보고합니다.
  - 단위·축척: 1 = 1m
  - 원점·방향: 홈플레이트 = 원점, 중견 = +Y, 위 = +Z
  - 객체 구성, 폴리곤 수, 재질
  - 조감도와 다른 점 목록
- 환경 확인: bpy venv, 네트워크, Gemini 키, Higgsfield 잔액.
- ★ 제원표와 모델 점검 결과 확인

**1단계 — 조감도에 카메라 맞추기**
- 조감도마다 알려진 치수로 카메라 위치·화각을 역산합니다. 알려진 치수: 베이스 간 27.432m, 투수판 18.44m, 파울라인 길이, 지붕 높이 등. 고척돔 가상투어 역산과 같은 방식입니다.
- 같은 카메라로 Blender 렌더 → 조감도와 겹친 비교 이미지를 만듭니다.
- `gemini_review.py`로 차이 목록을 얻은 뒤 광선 검사·겹쳐 보기로 검증합니다.
- ★ 비교 이미지 확인

**2단계 — 모델 고품질화 (Blender)**
- 지붕: 구조·외피·막, 트러스, 조명 기구.
- 관람석: 층별 단면(열 깊이·단 높이·경사), 통로·계단, 난간(유리·철제), 층 사이 벽·스카이박스·콘코스.
- 그라운드: 잔디·흙·워닝트랙·파울라인, 펜스, 폴, 그물, 더그아웃, 불펜.
- 전광판·띠 LED: 조감도 위치·크기.
- 재질: PBR, 실제 색에 맞춥니다.
- 좌석 생성 스크립트: 구역·열·번호·좌표·방향을 **하나의 JSON**으로 만듭니다. 웹(InstancedMesh·선택), 렌더(인스턴스·360° 지점), 배치도가 이 JSON을 함께 씁니다.
- **시야 자동 검사**(필수): 모든 렌더 지점에서 홈·마운드·1루·3루·폴 방향으로 광선을 쏩니다. 그라운드 전에 구조물에 막히면 보고합니다.
- ★ 조감도 비교 재확인 + 시야 검사 결과

**3단계 — 웹앱**
- `gocheok-dome-3d` 앱을 이식합니다. 구역/열/번호 선택, 배치도 창, 미니맵, 공유 링크, 모바일 UI, 야구·콘서트 모드(필요 시).
- 웹용 경량화: glTF + Draco/meshopt, 좌석 hi/lo LOD, Cycles 조명 굽기(라이트맵·정점색).
- 모바일에서 60fps에 가깝게 동작하는지 확인합니다.
- ★ Vercel 미리보기 링크 확인

**4단계 — 360° 사진급 시야**
- CPU로 저해상도 시험 렌더(조감도 시점 3~4개) → Gemini 검수 → 보정을 반복합니다.
- 렌더 지점: 구역마다 가운데 열. 6열 이상 구역은 맨 앞·맨 뒤 열을 추가합니다.
- 예산 계산: 지점 수 × 약 27초. 청라돔 장면이 더 무거우면 시험 1장으로 실측합니다.
- GPU(L40S, 71크레딧/시간)로 시험 1장 → 시간·비용 보고 → ★ 승인 → 전체 렌더 → 바로 반납합니다.
- 현재 잔액 161.66크레딧으로는 약 2시간이 한도입니다. 부족하면 충전 여부를 사용자에게 묻습니다.
- `pano_pack.py`로 WebP 변환 → 앱의 `src/pano.js`가 그대로 읽습니다.
- ★ 미리보기 확인

**5단계 — 공개**
- ★ 사용자가 승인하면 공개 주소(production)에 반영합니다.

### B-6. 완료 기준

- 조감도 3장 이상에서 같은 시점 렌더를 겹쳤을 때 주요 윤곽 오차가 화면 폭 2% 이내입니다. 대상은 지붕선, 관람석 층선, 펜스, 전광판입니다.
- Gemini 검수의 "high" 항목 중 검증된 것이 0건입니다.
- 시야 자동 검사에서 막히는 렌더 지점이 0곳입니다(의도된 기둥·그물 제외).
- 모든 구역에서 좌석 선택 → 시야 → 공유 링크가 동작합니다(PC·모바일).
- 360° 사진과 3D 모델의 방향이 일치합니다(같은 시선 스크린샷 비교).
- README에 자료 출처, 추정값, 파이프라인 실행 방법을 기록합니다.
